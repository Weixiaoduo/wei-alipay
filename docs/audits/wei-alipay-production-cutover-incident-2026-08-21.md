# Wei Alipay 生产切换与订单状态事故复盘

日期：2026-08-22
涉及事件：2026-08-20 插件切换、其后的 `missing-signature` 用户报告、2026-08-21 已付款订单被空回调改为失败
范围：`mall.weixiaoduo.com`、旧 `woo-alipay`、新 `wei-alipay`、FeiCode `Weixiaoduo/woo-alipay`
状态：事故已止损；根因分为“已证实”和“证据不足”，不得把推断写成定论。

## 1. 结论

这不是一个孤立的回调 bug，而是一轮支付插件切换中连续暴露的两个问题：

1. **切换验收不充分**：从旧插件切换到新插件时，同时改变插件入口、加载结构、密钥静态存储方式、支付表单净化和大量第一方支付代码。验收确认了 option、gateway ID、回调、历史订单和“密钥可解密”，但没有证明“迁移后的生产密钥能够用候选代码生成带非空 `sign` 的 RSA2 请求，并与支付宝登记的应用公钥形成同一密钥对”。用户随后报告支付宝 `missing-signature`。由于当时没有保存脱敏后的出站字段清单、签名预检结果和精确运行插件 SHA，`missing-signature` 的唯一代码级根因目前不能证实。
2. **旧回调可错误改变已付款订单**：恢复旧插件后，订单 42792 已有交易号且处于 `processing`，一次无有效支付宝字段的 GET 请求进入旧回调；旧代码把缺失 `app_id` 记为 `mismatched_app_id` 并把订单改为 `failed`。这条根因已有生产订单状态、请求形状和代码路径证据。

两者共同说明：支付插件的“代码、配置和页面健康”验收不能替代“密钥对、出站签名、支付宝受理、异步通知和最终订单状态”验收。

## 2. 影响

### 已证实

- 新支付入口曾向用户显示支付宝 `missing-signature`，正常下单链路不可用；当前普通上下文没有持续时长、失败订单数和受影响客户数，不能猜测。
- 订单 42792 的款项实际已到账，但 WooCommerce 状态从 `processing` 被改为 `failed`，存在延误履约和诱导重复付款的风险。
- 生产在 4.0.0 与旧 3.2.0 之间发生过切换/恢复，但从“4.0.0 已启用”到“3.2.0 实际启用”的中间操作没有完整时间线记录。

### 未证实

- 没有证据证明支付宝 SDK 文件本身在 2026-08-20 的 4.0.0 切换中发生变化。Git tree 显示 `d135d67` 与 `6698292` 的 `lib/alipay` tree 均为 `360df6e71c509eeeb872cdaf1f1855dd6b422c1f`。
- 仓库确有 2025-09-30 和 2026-04-05 的 SDK 更新历史，但不能把历史 SDK 更新自动归为本次 `missing-signature` 的直接根因。
- 没有保存出错请求的安全字段级快照，故不能在“私钥缺失、私钥格式不兼容、密钥对不匹配、表单过滤丢字段、错误插件实例、缓存旧页面”之间做唯一归因。

## 4. 变更面为什么被低估

4.0.0 不只是品牌改名。`d135d67..6698292` 还包括：

- 新 `Wei_Alipay_Secret_Store`，把私钥迁移为 AES-256-GCM envelope；
- 插件入口从 `woo-alipay.php` 改为 `wei-alipay.php`；
- 第一方支付类、回调、退款、订阅和模块代码大量修改；
- 支付跳转表单由原样输出改为 `sanitize_payment_form()`；
- 新更新器、构建、SBOM、语言包和多站点迁移；
- 旧核心、F2F、Huabei 三个插件与新聚合插件之间的激活关系变化。

虽然 gateway ID 和 option key 保留，但这只能说明数据地址没有改，不能证明运行时行为等价。

## 5. 根因与促成因素

### 5.1 切换事故

**已证实的流程根因**：生产切换门把“密钥 envelope 可解密”和“页面/类加载正常”错误地当成支付可用证据，没有把出站 RSA2 签名与支付宝受理设为阻断门。

**尚未证实的技术根因**：`missing-signature` 为什么出现。需要原始但已脱敏的出站字段、当时 active plugin 精确 SHA、私钥格式分类、密钥对指纹和 PHP/OpenSSL 错误才能确定。

促成因素：

1. 一次变更同时包含重命名、插件聚合、密钥迁移、支付代码安全修复、发布结构变化。
2. 克隆站使用测试私钥，只证明测试密钥能走迁移；没有验证生产私钥形状。
3. 记录只保存私钥长度和 envelope 状态，没有保存**不可逆公钥指纹**来证明迁移前后是同一密钥对。
4. 没有候选代码的离线 sign→verify 门，也没有生成支付表单的必填字段断言。
5. 没有沙箱端到端样本；记录明确写了真实支付样本为 0。
6. 首次切换已出现重复插件函数重声明和文件权限问题，却没有触发“停止当轮、重新评审整个切换包”。
7. 4.0.0 切换后的回退/恢复过程没有完整记录，导致后续只能从两个矛盾的运行状态反推。

### 5.2 已付款订单被改为失败

**代码根因**：旧回调在验证请求方法、必填字段和签名前就进入订单上下文判断，并允许无效请求把订单改成 `failed`。

促成因素：

1. 回调路由可被浏览器 GET 直接访问；
2. 无效通知没有纯只读、fail-closed 分支；
3. 已付款状态没有不可回退保护；
4. 回调错误与订单业务失败共用了状态变更；
5. 缺少“空 GET、缺签名、错误 app_id 均不得改变订单”的生产前合同。

## 6. 五问

1. 为什么顾客到支付宝后看到 `missing-signature`？——出站请求没有支付宝认可的非空签名字段。
2. 为什么生产切换前没有发现？——测试停在配置、解密、类加载、页面和合成订单，没有检查候选代码生成的最终支付表单及其签名。
3. 为什么没有检查最终签名？——切换清单按普通 WordPress 插件升级设计，没有把支付密钥对和支付服务商受理视为独立迁移对象。
4. 为什么失败后难以唯一定位？——没有记录脱敏字段清单、密钥指纹、精确运行 SHA、签名预检结果和完整回退时间线。
5. 为什么恢复旧插件后又发生订单误判？——旧回调缺少 fail-closed 输入门和已付款状态不可回退规则，回退包也没有经过事故场景回归。

## 7. 响应评价

### 做对的

- 没有把订单 42792 自动改回已付款，也没有自动退款；要求人工对账，避免二次资金错误。
- 回调热修前备份生产文件和配置；探针只发送空 GET/伪造签名，未发真实资金请求。
- 热修后确认无效请求返回 `fail` 且订单状态/备注变化为 0。
- 等价修复同步到 FeiCode 独立分支，没有擅自合并、Release 或再次部署。

### 需要修正的

- 把“私钥可解密”写成接近支付可用的结论；以后必须写成“存储层预检通过，签名和服务商验收未完成”。
- 没有在首次切换异常后停止整轮变更。
- 没有明确区分 SDK tree 是否变化、密钥存储是否变化、密钥对是否变化。
- 没有记录从 4.0.0 回到 3.2.0 的操作、时间、执行人、审批和验证。

## 9. 密钥恢复与轮换原则

“重新获取私钥”必须拆成两种情况：

1. **恢复原私钥**：从原密钥工具目录、受限备份或旧配置恢复；用私钥导出应用公钥并比较支付宝平台登记指纹。不能在普通日志、文档或命令输出中显示私钥。
2. **轮换密钥对**：原私钥无法恢复或格式不兼容时，本地生成新密钥对，在支付宝开放平台更新对应应用公钥，并在同一受控窗口更新插件私钥。两端任何一侧单独变化都必须 fail closed。

支付宝官方 PHP SDK 要求应用提供 AppID、应用私钥和与模式对应的支付宝公钥/证书；公钥模式与证书模式是不同配置，不得混用。参考：<https://github.com/alipay/alipay-sdk-php-all/blob/master/v2/README.md>。

## 10. 仍缺的证据

- `missing-signature` 当时的精确时间、订单、浏览器页面源代码和脱敏后的表单字段名；
- 当时 active plugin 文件 SHA 与候选 SHA 的一致性；
- 生产私钥是裸 PKCS#1、PKCS#8 PEM、文件路径还是其他格式；
- 从该私钥导出的应用公钥指纹与支付宝登记值是否一致；
- 4.0.0 回退到 3.2.0 的完整操作记录；
- `missing-signature` 影响的订单数、持续时间和客户数。

这些缺口不影响建立新门禁，但在证据补齐前不能声称已经得到唯一技术根因。
